Validación y pruebas de conectividad

MÓDULO 03 · SQL SERVER

Demuestra con evidencias independientes que el servicio escucha, la red permite llegar al puerto, SQL Server autentica al usuario y los permisos respetan el alcance del perfil analítico. Puerto objetivo: 51433.

⚙️ NETSTAT 📡 TEST-NETCONNECTION 🔑 SSMS + PERMISOS
OBJETIVO DE LA MISIÓN // QUÉ DEBES LOGRAR

🎯 META

Validar por capas que la configuración de red y autenticación funciona de extremo a extremo. Cada herramienta observa una parte distinta del proceso; un resultado positivo en una prueba no sustituye a las demás.

CAPAS DE VALIDACIÓN // QUÉ SE COMPRUEBA EN CADA UNA
01

SERVICIO

Motor iniciado y disponible

02

PUERTO

51433 en LISTENING

03

TCP llega al servidor

SQL SERVER

Autenticación aceptada

Datos de la conexión

ACTIVIDADES Y EVIDENCIAS // PRUEBAS DOCUMENTADAS
01

Comprobar el puerto con NETSTAT

Verifica que SQL Server esté escuchando en el puerto 51433.

  • En el servidor ejecuta: netstat -ano | findstr 51433
  • Busca una línea con estado LISTENING asociada al proceso del motor.
EJEMPLO DE SALIDA
TCP    0.0.0.0:51433    0.0.0.0:0    LISTENING    2456
✓

Resultado esperado: puerto TCP 51433 en LISTENING.

02

Probar conectividad con Test-NetConnection

Desde el equipo cliente verifica si existe comunicación TCP con el servidor.

  • Ejecuta (sustituye la IP por la real del servidor):
POWERSHELL
Test-NetConnection -ComputerName 192.168.1.50 -Port 51433
✓

Resultado clave: TcpTestSucceeded : True

ℹ

Una prueba TCP exitosa no demuestra que el login sea válido ni que tenga permisos. Solo confirma que existe comunicación con el puerto.

03

Obtener la dirección IP del servidor

En el equipo donde está instalado SQL Server ejecuta ipconfig y documenta la IPv4 real utilizada (no copies IPs de ejemplo del material).

04

Conectar desde SSMS (conexión remota)

Desde el equipo cliente establece la conexión al motor.

  • Abre SSMS en el cliente.
  • Server name: tcp:,51433
  • Autenticación: SQL Server Authentication
  • Login: analista_upla + contraseña del laboratorio
✓

Resultado esperado: conexión exitosa usando el puerto 51433 y el login analista_upla.

05

Validar autenticación y permisos

5A — Prueba de lectura permitida:

T-SQL · PERMISO DE LECTURA
USE ProyectoAnalitico_UPLA;
GO

SELECT
    HAS_PERMS_BY_NAME(
        DB_NAME(),
        'DATABASE',
        'SELECT'
    ) AS PermisoLectura;
GO
✓

Esperado: PermisoLectura = 1

5B — Prueba de restricción (debe fallar):

Intenta crear una tabla u otra operación de escritura/DDL. El rechazo por permisos es la evidencia de que el control de acceso funciona. No “arregles” el error concediendo permisos extra.

06

Revisar la sesión con vistas del sistema

Consulta información de la conexión establecida (por ejemplo con sys.dm_exec_connections u otras DMV) para documentar que la sesión corresponde al login y al puerto esperados.

ÁRBOL DE DIAGNÓSTICO // SI ALGO FALLA
Resultado observado Posible causa Siguiente comprobación
No aparece LISTENING Servicio detenido, TCP/IP off o puerto distinto Servicio + protocolos + puerto
TcpTestSucceeded : False IP incorrecta, firewall o ruta de red IP, puerto y regla de entrada
TCP OK, SSMS rechaza Credenciales, modo auth o login deshabilitado Login y método de autenticación
Conecta pero consulta denegada Falta permiso en esa base Usuario, roles y permisos

Criterio de aceptación: la conectividad se considera validada cuando se demuestra, con evidencias independientes, que el servicio escucha, la red permite llegar al puerto, SQL Server autentica al usuario y los permisos respetan el alcance del perfil analítico.

MISIÓN 03 COMPLETADA · LABORATORIO CERRADO

Con la configuración de red, la autenticación de menor privilegio y la validación por capas, SQL Server queda como una plataforma segura, estable y confiable. El puerto 51433, el login analista_upla y las pruebas documentadas cierran el ciclo de la misión.
